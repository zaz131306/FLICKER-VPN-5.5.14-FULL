## 2. Defect A (главный): браузер вооружён на порту, где никто не слушает

Шапка дампа, 22:00:10:

```
узел            : Диагностика (direct)
режим           : smart
статус          : connected
прокси браузера : вооружён, 127.0.0.1:1080
host SOCKS      : не слушает
```

То есть: выбран **локальный транспорт** (узел «Диагностика (direct)»,
`protocol: "direct"`), для которого native host не поднимается вовсе и
SOCKS-слушателя не существует в принципе. А расширение при этом:

1. вооружило браузеру ручной прокси на `STATE.socksPort` (1080) —
   `applyProxyModeNow()` не различал «туннель через хост» и «локальный
   транспорт»;
2. гоняло пер-реквест трафик в тот же порт (`perRequestDecision` строил
   ruleset по протоколу, а не по факту наличия слушателя);
3. считало такой туннель «подтверждаемым»: `handleVerifyResult()` принимал
   подтверждение для узла, у которого нечего подтверждать.

Итог для пользователя: статус «connected / прокси активен», а браузер смотрит
в мёртвый порт — ни VPN, ни интернета. Именно это ты описал как
«туннель не работает, прокси возвращается браузеру».

**Что сделано (A1–A4):**

* `perRequestDecision()`: `protocol === "direct"` (не DPI) → **DIRECT** до всякой
  маршрутизации — запросы локального транспорта никогда не идут в SOCKS;
* `applyProxyModeNow()`: отдельная ветка **local-direct** → `setProxyNone()`,
  `tunnelVerified = true`, `proxyMode = "local-direct"`, запись в журнал
  `local-direct`, `broadcastUI({type:"directNode"})`; ветка идемпотентна
  (повторный вызов не дёргает настройки прокси);
* `handleVerifyResult()`: для локального транспорта — no-op (нечего
  подтверждать и нечего держать);
* `verify` больше не снимает подтверждение с local-direct.

## 3. Defect B: HOLD на мёртвом конце, продлённый пробным прогоном

```
22:04:09 verify: туннель больше не подтверждён → HOLD
22:04:17 probe: старт 600 серверов (mode=full)
22:06:06 switch: direct → 64.176.2.21, порт 1080 занят → 1081, перевооружение
22:10:37 probe: готово — 32 живых из 600 (6 мин 20 с)
```

Твоё требование: «прокси вообще не должен выкидываться браузеру». Оно осталось
в силе, но шестой дамп показал его обратную сторону: **держать мёртвый порт —
это то же самое, что выбросить прокси**, только без интернета и с панелью, которая
врёт. С 22:00:10 до 22:06:06 браузер был прибит к 1080, где никто не слушал
(узел-то был `direct`), а HOLD продлевался «прогрессом»: пока хост жевал пробу
600 серверов, ветка `probeRunning()` на каждом цикле подтверждения вызывала
`markHoldProgress("хост занят пробой серверов…")`, и окно без прогресса
(120 c) не закрывалось.

**Что сделано (B1–B5):**

* `endpointDead()` — конец заведомо мёртв, если: транспорт локальный, **или**
  native host не на связи (`nativeOnline === false`), **или** последний
  `diagnose` сказал `socksListening === false` и это не старше 60 c;
* `canHold` / `wantHold`: при `endpointDead()` удержание **запрещено** —
  прокси освобождается сразу, в журнал пишется `hold-refused` с причиной,
  в лог хоста уходит `dbg: proxy: HOLD отменён (…) — мёртвый порт не держу`;
* ветка пробного прогона больше не зачитывает прогресс на мёртвом конце:
  `if (!endpointDead()) markHoldProgress("хост занят пробой серверов…")`;
* `diagnose` запоминает `lastSocksListening` + `lastDiagnoseAt` — по ним
  `endpointDead()` отличает «слушатель вот-вот вернётся» от «держать нечего».

Удержание на **живом** конце не тронуто: HOLD по-прежнему заводится, продлевается
реальным прогрессом и закрывается по окну без прогресса (120 c) или по потолку
(300 c) — постоянная дыра в интернете не появляется. Это покрыто тестами
`hold-progress`, `hold-proxy` и новым `hold-refusal` (регрессионный страж).

## 4. Defect C: мёртвые ноды не определялись никогда

```
22:06:47 liveness: контрольный dial через туннель не удался: socks5: connect отклонён (код 0x1)
22:06:47 dbg: soft liveness: tunnelAlive=false проигнорирован (SOCKS слушает, подряд 1, трафик есть)
22:07:34 liveness: … отклонён (код 0x1)          ← и снова ничего
22:10:37 probe: готово — 32 живых из 600
рейтинг: доверенных 0, мёртвых 50, без истории 1755
```

Правило из 5.5.10 («смерть ноды») требовало **трёх** отказов dial подряд **и**
45 c **и** нулевого трафика. В жизни оно не срабатывало никогда:

* серия обнуляется при каждой смене ноды (`softLivenessReset`), а ноды в твоём
  дампе переключались каждые 20–40 c;
* «нулевого трафика» не бывает: контрольные запросы самого расширения идут через
  туннель и дают байты. В шапке при этом `Передано ↑0.00 ↓0.00 MB` — и рядом
  «трафик есть».

Расширение сидело на ноде, которая не пропускает трафик, и писало «Туннель жив».

**Что сделано (C1–C2): вердикт по двум независимым подтверждениям.**

На `tunnelAlive === false` расширение теперь **само** гоняет контрольный запрос
браузера через SOCKS (`probeThroughProxy`) и решает по его результату:

* запрос **не прошёл** → два независимых подтверждения (dial хоста + наш запрос)
  → `declareSoftDead()` **сразу**: без 45 c, без требования нулевого трафика,
  без трёх отказов подряд. Нода уходит в мёртвые, лестница переключается на
  другую;
* запрос **прошёл** → нода рабочая, dial хоста игнорируем (он просто не
  уложился в свой таймаут на медленной ноде) и пишем об этом в лог:
  `soft liveness: dial хоста не прошёл, но контрольный запрос браузера через
  SOCKS прошёл — нода рабочая`.

`declareSoftDead()` — общая функция: кулдаун внутри, журнал `soft-dead`,
`noteTunnelDeath()`, `recoverFromDeadTunnel()` (лестница). Прежнее мягкое
правило сохранено как запасной путь и теперь вызывает ту же функцию.
Вердикт отбрасывается, если устарел (порт сдвинулся, статус сменился,
пользователь ушёл на другую ноду), и не мешает ветке предупреждения в UI
(`livenessWarn` остаётся).

## 5. Defect D: панель больше не врёт

* `statusPayload.proxyBlockedReason` — почему прокси не вооружён
  (локальный транспорт / мёртвый конец / пользователь снял вручную);
* `dbg` при смене режима печатает **фактический** `STATE.proxyMode`, а не
  намерение;
* `options.js`, панель диагностики:
  `Прокси браузера: не вооружён  ← выбран локальный транспорт (НЕ VPN), трафик
  идёт напрямую  (<причина>)`;
* dbg локального транспорта печатает факт, а не намерение:
  `proxy=none (локальный транспорт direct: SOCKS-слушателя нет, трафик идёт
  напрямую — это НЕ VPN)`;
* вердикт о мёртвой ноде в логе хоста: `soft liveness: DEAD <причина>`.

## 6. Что расширением не чинится (честно)

* **Подписка.** Проба 600 серверов за 6 мин 20 с дала **32 живых** (~5 %).
  Рейтинг: доверенных 0, мёртвых 50, без истории 1755. Это состояние списка
  нод провайдера, а не кода. 5.5.14 не оживит мёртвые ноды — она перестаёт
  выдавать их за живые, определяет смерть за секунды (а не никогда) и уходит с
  такой ноды сама.
* **Native host 5.5.4.** Go-исходников нет, хост не менялся; его `dial`
  по-прежнему бывает медленным/отказным на живых нодах — поэтому вердикт
  теперь выносится по двум источникам, а не по его слову.

## 8. Как проверить в поле (2 минуты)

1. Поставь `flicker-vpn-5.5.14-SIGNED.xpi`, перезапусти Firefox,
   `about:addons` → FLICKER VPN → **5.5.14**.
2. Выбери узел «Диагностика (direct)». В «Дополнительно» → диагностика панель
   должна показать: `Прокси браузера: не вооружён ← локальный транспорт (НЕ VPN)`,
   а интернет — работать напрямую. В логе хоста появится
   `dbg: proxy: локальный транспорт — прокси не вооружаю`.
3. Подключись к VPN-ноде и дождись обрыва (или выбери заведомо мёртвую из
   подписки). Ожидаемое в логе хоста:
   * если хост слушает SOCKS → `proxy HOLD: …` и восстановление на месте;
   * если хост сказал «не слушаю» → `proxy: HOLD отменён (…) — мёртвый порт не
     держу`, в журнале метка `hold-refused`, браузер сразу на прямом трафике.
4. На мёртвой ноде в течение секунд (а не 45 c и не никогда) должно появиться:
   `soft liveness: узел не пропускает трафик: контрольный dial хоста отклонён
   (1-й раз) И контрольный запрос браузера через SOCKS не прошёл: …` →
   `обрыв ноды …` → переключение на другую.

## 9. Журнал: метки

Новые: `hold-refused`, `local-direct`. `soft-dead` теперь ставится из двух
источников (прежнее мягкое правило и новый вердикт по двум подтверждениям) —
текст причины различает их.

Прежние: `switch-stop-ack`, `tunnel-mode-noop`, `host-disconnect-recovery`,
`port-shift`, `verify-stale`, `verify-orphan`, `verify-unconfirmed`,
`restart-loop`, `switch-noop`, `tunnel-mode`, `hold-start`, `hold-expired`,
`progress`, `stage`, `release`.
